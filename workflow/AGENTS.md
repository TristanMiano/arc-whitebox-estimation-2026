# Repository agent instructions

This is an ARC White-Box Estimation research project. The default objective is
to improve actual official adjusted score quickly, while preserving a reliable
submission and honest evidence. Work on one owner-authorized task at a time.

## Read and choose scope

Start with `START_HERE.md`, `state/current_state.json`, the **active queue** in
`TODO.md`, and `docs/COMPETITIVE_RESEARCH_LOOP.md`. Then read only the relevant
candidate specification, prior results and owner directives. Search
`ALGORITHM_LEDGER.md` before creating a new variant. Do not treat the first
unchecked historical or parked checkbox as the next task.

The owner's latest instruction takes precedence. The prospective submission
workflow is defined in `docs/COMPETITIVE_RESEARCH_LOOP.md` and mirrored in
`state/competitive_research_policy.json`. `RESEARCH_PROTOCOL.md` explains data
and evidence handling. Full science is optional and separately scoped in
`docs/SCIENTIFIC_RESEARCH_PROTOCOL.md`; old task-specific gates do not become
requirements for a new submission attempt.

## Default execution

- Rank candidates by expected official improvement per remaining hour,
  including implementation, qualification, repairs and grading. Re-rank after
  new evidence; return to theory early instead of exhausting a weak queue.
  This is a planning aid, not a rule that the easiest small gain always wins.
  A lower research-stage success probability can justify an attempt when the
  gain and information value are larger. The roughly90% submission screen is
  not a probability threshold for selecting research or implementation work.
- During research, record a cheap candidate as a fallback when a credible
  larger-gain thread is available, and prefer developing that thread. Balance
  upside, probability, remaining work and information value within the task's
  budget; finding a ready candidate does not itself end a recurrence.
- Use the actual Python/Whest path for submission prototypes and evaluation.
  A native scientific replica, F0--F3 funnel, multi-block validation campaign,
  ablation suite or P1/R1/P2 tier is not a submission prerequisite.
- For a chosen submission candidate, meter an integrated full-shape fixture
  early. Default to a small paired
  comparison, usually 12 predetermined networks, and roughly 90% support for
  a lower adjusted mean. Reuse appropriate existing evidence. Stop local
  testing when the submission decision is clear; no extra confidence or
  minimum-effect gates. Follow the bounded extension rule in the main policy.
- Qualify the actual package, then submit within existing owner authority.
  Asking to execute a submission task authorizes upload and monitoring. Allow
  60 minutes per attempt and at most one unchanged-package retry for a generic
  evaluator problem. Official feedback is part of the development loop.
- Theory tasks allow numerous small experiments throughout the derivations:
  derive, probe, interpret, revise. An authorized recurrence includes partial
  prototypes, small development comparisons and targeted parameter/rank
  sensitivities; no separate owner permission or complete algorithm is needed
  for each probe. There is no fixed probe-count limit or 90% exploratory gate.
  Use the smallest informative scale and track cumulative cost and learning.
- The default theory floor is **120 active research minutes**, including at
  least **60 minutes of written mathematics**. The added time supports empirical
  design, prototype work and interpretation; spend it on further derivation
  when another probe would teach little. Preserve larger task-specific floors.
  Count overlapping work once; idle waiting, packaging and routine records do
  not count. Zero to two final nominees does not limit exploratory hypotheses
  or variants. Stop after the authorized task; a ready small win does not end
  research while a credible larger-upside thread deserves the remaining time.

## Integrity and implementation

1. Optimize arithmetic mean adjusted final-layer score, with actual FLOPs and
   the current multiplier. Distinguish local evidence, projections and grades.
2. Identify material changes before testing. During research, a short scratchpad
   or batch entry with a local probe ID, question, source/version, inputs and
   comparator is sufficient; retain executed code and outputs. Adaptive changes
   get a new local label, without a full algorithm registry entry per micro-run.
   Declare exploratory data and permit repeated feedback there. Register and
   freeze the selected ALG variant before its submission-facing comparison;
   disclose prior exposure and never relabel exploratory results as fresh
   validation. Historical freezes and the final blind block remain protected.
3. Use only permitted numerical/accounting APIs in submissions. No grader-state
   access, hidden seeds, untracked numerical work or accounting circumvention.
   Keep finite full-shape output, deterministic shipped-design replay, resource
   compliance, archive identity and appropriate fallback checks.
4. Preserve raw results, frozen manifests, failed attempts and the strongest
   retained positive evidence. Distinguish a scientific/competitive loss from
   a numerical, packaging, host or external-service failure.
5. Numerical equivalence to historical outputs and current-package byte replay
   are distinct checks. Use a justified recorded tolerance where appropriate;
   do not retroactively rewrite a historical exact-byte result.
6. Reuse passing checks and the relevant working environment. T118A/T120B
   qualify WSL/Linux submission execution. The old Windows-first fault history
   does not require repeating a failed platform before every task. A separately
   chosen native scientific workload retains its applicable native contract.
7. Diagnose and repair routine problems within the task's bounded scope. Ask
   for owner intervention only when a concrete remaining action needs it.
   Do not add clean-run streaks, reflexive machine audits or blind reboots.
8. Record start, estimated time, end, actual duration and estimate error.
   Produce one concise task result, an event row and the relevant ledger/state
   changes. Reuse immutable evidence; run only checks affected by the change.
   Commit scoped work when practical and preserve unrelated workspace changes.
9. Never commit credentials or private challenge data. Public-input prediction
   evidence is permitted. Keep per-network records and source/package hashes.
